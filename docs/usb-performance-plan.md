# USB 复制开销实测方案

用户授权自主完成第一步测量；仅当 CPU 整帧复制被证实为主要吞吐/错误瓶颈时，继续 DMA-BUF 共享改造。保持当前 PS/PL、传感器、内核、USB描述符、缓存同步和帧缓冲归属不变。

1. 应用增加默认关闭的 --profile，测量 memcpy墙钟与进程CPU时间、采集软件完成到DQBUF、DQBUF到UVC QBUF返回、QBUF调用、QBUF到DQBUF归还及提交间隔。
2. 固定大小直方图记录延迟分布，每秒输出累计统计；p50/p95/p99明确为桶上界。统计窗口从本次USB流第一次发送开始，CPU百分比按单核100%计算，USB结束后冻结最后活动时间，排除长时间等待主机造成的稀释。采集时间戳是驱动软件完成，不是传感器曝光/SOF，不作为glass-to-glass延迟。
3. 单元测试覆盖统计边界、正常/冻结模式输出、源数据不变及capture/DP归属不变，运行原所有权、事件、快照、序号及USB错误分类测试。
4. 先RAM运行；使用同一FFmpeg、SuperSpeed端口和线缆、1280x1024 YUY2 120fps、512MiB主机缓冲，DP保持120Hz。匹配正常复制A与 --profile-static-usb 对照B。B每个输出槽只复制一次，因此USB画面冻结，绝不是可交付的真实摄像头方案；摄像头、采集和DP仍持续运行。它只消除重复复制，用于检查吞吐和错误是否随之明显变化。
5. 比较主机实际收到的帧数、设备提交/归还、分类ERROR、invalid、DP进度、复制耗时与进程CPU。初始调试、启动失败、提前停止窗口单列，不作匹配A/B。
6. 若去掉重复复制不能提高稳态吞吐且仍出现同类ERROR，则不将复制定性为当前主要瓶颈，不凭省CPU的好处改写已验证的多消费者归属协议。DMA-BUF驱动源码支持仅为初步可行性证据，不能等同于端到端验证。
7. 测试后退出冻结模式，恢复真实摄像头与现有QSPI启动应用；不以诊断模式替换正式固件。
